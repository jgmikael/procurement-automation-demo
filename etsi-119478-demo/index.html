ETSI TS 119 478 Semantic Data Specifications

Three Approaches to Semantic References in Digital Credentials

ETSI TS 119 478 V1.1.1 defines how attributes in electronic attestations should be semantically anchored. This interactive demo shows three levels of semantic specification, from simple property URIs to comprehensive data specifications with multiple schema distributions.

WE BUILD Approach: Direct Property URI

Term-level semantic anchoring
✓ Current WE BUILD WP4 Semantics Implementation
This approach provides direct, precise semantic anchoring by referencing individual vocabulary properties. Each attribute points directly to its ontology term.

Key advantage: Semantics remain format-independent. The same EBWV property can underpin SD-JWT VC, W3C VC/JSON-LD, mdoc, XML, or future formats.

Example: EU Company Certificate Attributes

Attribute Semantic Reference Definition
legalName https://w3id.org/ebwv#legalName Legal name of the undertaking as registered
legalForm https://w3id.org/ebwv#legalForm Legal form type (GmbH, AG, Ltd, etc.)
registeredAddress https://w3id.org/ebwv#registeredAddress Postal address where company is registered
legalIdentifier https://w3id.org/ebwv#legalIdentifier EUID or similar unique legal identifier

ETSI Model: URI of Attribute Specification

Specification-level semantic data description
📘 ETSI TS 119 478 Definition
ETSI defines a semantic data specification as:

"A specification, with human- and/or machine-processable representations, defining how data is organised, described and interpreted."

The semanticDataSpecification element is a URI identifying the specification as a whole, not just one vocabulary term.

⚠️ Important Distinction
ETSI's semantic data specification ≠ Single vocabulary term

An individual OWL property URI (ebwv:legalName) is not equivalent to ETSI's broader notion of a semanticDataSpecification.

ETSI's wording suggests that the latter normally identifies a complete data specification, not merely one vocabulary term. The specification should be a structured, standardized, and media type-agnostic definition describing the attribute's data elements, semantics, and relationships.

Four Models: Semantic Reference Approaches

From direct property URIs to schema-only references
📐 Four Ways to Reference Semantics
ETSI TS 119 478 and related standards define multiple approaches for semantic references in attestation catalogues and data specifications. This section compares four distinct models for referencing the semantics of an attribute like legalName.

Model A: Property URI

Direct reference to semantic property

https://w3id.org/ebwv#legalName
  • Points directly to OWL property
  • Simple, unambiguous
  • Minimal infrastructure
  • Used by WE BUILD now

Model B: Attribute Specification URI

Reference to attribute specification document

https://specifications.webuild.eu/
  /eucc/attributes/legal-name/1.0
  • Specification with constraints
  • Multiple schema distributions
  • Format-independent
  • ETSI TS 119 478 compliant

Model C: Attestation Profile URI

Reference to attestation/application profile

https://specifications.webuild.eu/
  /eucc/1.0
  • Entire attestation specification
  • All attributes bundled
  • Use case specific
  • Less granular

Model D: Schema URI Only

Reference to JSON Schema file

https://schemas.webuild.eu/
  /eucc-schema.json
  • ❌ No semantic meaning
  • ❌ Only structure validation
  • ❌ Format-dependent
  • ❌ Not recommended
⚠️ Why Model D (Schema-Only) Is Insufficient
JSON Schema alone cannot serve as a semantic foundation:
  • No semantic meaning: JSON Schema defines structure and validation rules, but not what the data means
  • Format-specific: Locked to JSON representation, cannot be applied to XML, CBOR, or other formats
  • No interoperability: Different schemas for same concept cannot be automatically recognized as equivalent
  • No reasoning: Cannot infer relationships, hierarchies, or equivalences

Example: Two schemas might both have a "legalName" field, but without semantic reference, a machine cannot determine if they mean the same thing.

Three-Layer Architecture

Separation of concerns: Catalogue → Specification → Property
🏗️ Layered Semantic Architecture
ETSI TS 119 478 implies a three-layer architecture for semantic references:
  1. Catalogue Layer: Attestation catalogue defines attributes (e.g., "EUCC legalName")
  2. Specification Layer: Semantic data specification document with constraints and distributions
  3. Property Layer: EBWV/OWL property definition with semantic meaning

Purpose: Define semantic meaning, relationships, domain/range
Enables: Machine reasoning, interoperability, equivalence detection

Separation of Concerns

🎯 OWL (Layer 3)

Semantic Meaning

  • What: Defines what a property means
  • Domain/Range: What it applies to and what values it can have
  • Relationships: Equivalence, subproperties, inverses
  • Reasoning: Enables logical inference

Example: ebwv:legalName is a property of ebwv:LegalEntity, equivalent to schema:legalName

✅ SHACL (Layer 2)

Validation Constraints

  • What: Defines validation rules and constraints
  • Cardinality: Minimum/maximum occurrences
  • Patterns: Regular expressions, formats
  • Validation: Check if data conforms

Example: legalName must be 1-255 chars, contain only letters/numbers/punctuation

📋 JSON Schema (Layer 2)

Structure & Validation (JSON-specific)

  • What: Defines JSON structure and validation
  • Types: string, number, array, object
  • Format: JSON-specific constraints
  • Validation: JSON document conformance

Example: {"legalName": {"type": "string", "minLength": 1}}

🎓 Key Insight: Why All Three Are Needed

Each layer serves a distinct purpose:

  • OWL (Semantic): Tells machines what it means → Enables interoperability across systems
  • SHACL (Constraints): Tells machines how to validate → Works across all RDF formats
  • JSON Schema (Structure): Tells machines JSON structure → Only for JSON documents

Example scenario: Two organizations both use ebwv:legalName (OWL), but one requires 1-100 chars (SHACL) and the other 1-255 chars. They can still recognize the semantic equivalence and map between systems, even though validation rules differ.

⚠️ Without OWL: Two schemas with "legalName" fields are just strings to a machine. No way to know if they mean the same thing, are equivalent, or can be mapped.
